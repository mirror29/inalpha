# Power BI Prototype — Data Model, Lineage Dashboard & Drill-Through

## Overview
This document explains how to reproduce the Power BI prototype using the synthetic CSV fixture generated by the Python dataset generator.

The prototype consists of:
1. Generating the synthetic datasets.
2. Importing the generated CSV datasets into Power BI.
3. Building the relational data model.
4. Creating the Realised PnL measure & Net Equity Change tracking.
5. Creating the lineage/decomposition-tree dashboard.
6. Configuring tooltips and drill-through.
7. Creating the run-performance dashboard.
8. Connecting the two pages through drill-through.
9. Verifying that filtering, exception inspection, and drill-through work correctly.

The prototype is intended to demonstrate how candidate → backtest run → trade/fill lineage can be explored interactively, alongside an isolated workflow for inspecting validation exceptions. Representative risk/performance metrics are synthetic display values; `metrics_validated` remains false. The structural pass flag describes the checks on the generated tables, not independent validation of all metrics.

## 1. Input Data
The Power BI model uses the CSV files generated by the synthetic Python dataset generator.

The generator produces four files in the `fixture_output` directory:
- `candidates.csv` (Strategy/candidate-level information)
- `backtest_runs.csv` (Backtest execution and performance information)
- `backtest_trades.csv` (Individual trade/fill-level information)
- `validation_exceptions.csv` (Imported separately to preserve the clean 1:* relational model)

**Generating the Data:**
The Python generator should be executed first so that these CSV files are available locally. Run the following commands in your terminal:

```bash
# Install dependencies
pip install pandas

# Run the generator
python "Generate data for model.py"
```

## 2. Importing the Data into Power BI
Open Power BI Desktop.
From the Home tab:
1. Select **Get data**.
2. Select the appropriate **CSV/Text** source option.
3. Import the files from your `fixture_output` directory:
   - `candidates.csv`
   - `backtest_runs.csv`
   - `backtest_trades.csv`
   - `validation_exceptions.csv`
4. Load all four datasets into the Power BI model.

The expected table names in the Data pane are:
- `candidates`
- `backtest_runs`
- `backtest_trades`
- `validation_exceptions`

## 3. Building the Data Model
After importing the CSV files, open **Model view**.

### 3.1 Candidate → Backtest Run Relationship
Create a relationship between:
`candidates[candidate_key]` and `backtest_runs[candidate_key]`
- **Cardinality:** One-to-many (1:*)
- The `candidates` table is the one side and `backtest_runs` is the many side.

### 3.2 Backtest Run → Backtest Trade Relationship
Create a relationship between:
`backtest_runs[run_key]` and `backtest_trades[run_key]`
- **Cardinality:** One-to-many (1:*)
- The `backtest_runs` table is the one side and `backtest_trades` is the many side.

### 3.3 Exception Relationship
Create a relationship between:
`backtest_runs[run_key]` and `validation_exceptions[run_key]`
- **Cardinality:** One-to-many (1:*)
- The `backtest_runs` table is the one side and `validation_exceptions` is the many side. 

Use active, single-direction relationships from candidates to runs and from runs to fills/exceptions. Do not activate the latest-run soft reference. Use `backtest_runs[run_key]` as the drill-through anchor so the selected run filters its fills and exceptions.

### 3.4 Model Structure
The final model should visually represent:

```text
┌────────────────────────────┐
│         candidates         │
└─────────────┬──────────────┘
              │ 1 : *
              ▼
┌────────────────────────────┐       1 : *    ┌────────────────────────────┐
│       backtest_runs        ├───────────────►│   validation_exceptions    │
└─────────────┬──────────────┘                └────────────────────────────┘
              │ 1 : *
              ▼
┌────────────────────────────┐
│      backtest_trades       │
└────────────────────────────┘
```

## 4. Creating the Core Measures
Create the following new measures in Power BI:

**1. Gross Realized P&L:**
`Total Gross Realized P&L = SUM(backtest_trades[realized_pnl])`
*This measure is used as the primary value for the lineage/decomposition analysis.*

**2. Net Equity Change:**
`Net Equity Change = SUM(backtest_runs[final_equity]) - SUM(backtest_runs[metric_initial_cash])`
*This factors in fees and initial cash layouts. It must remain visually separate from Gross Realized P&L.*

## 5. Creating the Lineage Dashboard
The first dashboard page is the lineage/exploration page.
Its purpose is to allow the user to start from the overall PnL and progressively break it down through:
`PnL` → `Candidate` → `Run` → `Symbol` → `Timeframe`

### 5.1 Add the Decomposition Tree
Create/select the Decomposition Tree visual.
- **Analyze:** `Total Gross Realized P&L`
- **Explain by** (in this exact order):
  1. `candidates[candidate_key]`
  2. `backtest_runs[run_key]`
  3. `backtest_runs[symbol]`
  4. `backtest_runs[timeframe]`

## 7. Drill-Through Configuration
The run-performance dashboard is accessed through drill-through.
On the run-performance page, enable:
- **Cross-report:** Off (both pages belong to this report)
- **Keep all filters:** On

Add the drill-through fields:
- `backtest_runs[run_key]`

Use the run key as the required drill-through field. Keep all filters preserves any additional candidate, symbol, and timeframe context. This also allows the exception table, which identifies a run, to reach the same page.

## 8. Run Performance Dashboard
The second page provides a detailed view of the selected candidate/run.
It contains:
- Candidate & Run identifiers
- KPI cards
- Realised PnL chart, Fee chart, Price chart
- Separate P&L, fee, and price displays

## 9. Dashboard KPI Cards
Configure the following KPI cards:
- **Candidate Key:** `backtest_runs[candidate_key]`
- **Run Key:** `backtest_runs[run_key]`
- **Total Gross Realised PnL:** Measure created in Section 4.
- **Total Fee:** `backtest_runs[total_fees]`
- **Total Fills:** `backtest_runs[reported_num_trades]` (rename visual label to "Total Fills")
- **Win Rate:** `backtest_runs[win_rate]`
- **Fitness:** `backtest_runs[fitness]` (the selected run’s fitness)

## 10. Run Performance Line Chart
- **X-Axis:** `backtest_trades[seq]`
- **Values:** `backtest_trades[realized_pnl]`, `backtest_trades[fee]`, and `backtest_trades[fill_price]`. Use separate charts or axes for P&L/fees and price; they are not additive components.

Show P&L, fee, and fill price separately. Do not use a parts-of-whole chart combining price with aggregate P&L or fees.

## 21. Exception Inspection Workflow
The generator computes the equity exception from the current synthetic values and exports `validation_exceptions.csv`. The equivalent `equity_consistency_check.sql` can independently check the Power BI fixture after importing its run/fill CSVs into SQLite. This query is separate from the 30 general checks because it requires the explicit zero-unrealized-P&L assumption.

**Test Case: Equity Consistency Mismatch**
The `validation_exceptions.csv` dataset contains a deliberate mathematical failure for run `R002`. 
*(Note: The equity identity logic here strictly assumes 0 unrealized P&L, which aligns with the synthetic fixture's design assumptions. It is not generally valid for portfolios carrying open positions).*

**Steps to Inspect:**
1. Navigate to the **Exceptions Table** (create a basic table visual on the main page).
2. **Crucial Configuration:** Ensure you pull `run_key` from the `backtest_runs` table (`backtest_runs[run_key]`), NOT from `validation_exceptions`, to satisfy Power BI's cross-table drill-through requirements. Pull `check_name`, `status`, and `details` from `validation_exceptions`.
3. Locate the failed record for `run_key` = `R002`. The table will display the check (`equity_consistency_check`) and the error details (`Equity mismatch detected: expected 12110.87, actual 12160.87`).
4. Right-click the `R002` row in the Exceptions Table and select **Drill through -> Run Performance Dashboard**.
5. The destination page will automatically filter to `R002`. Inspect the trade table and KPI cards on the Run Performance Dashboard to identify the mathematical discrepancy.
