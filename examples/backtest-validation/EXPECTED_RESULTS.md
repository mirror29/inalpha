# Expected Synthetic Validation Results

This document describes the expected results when the validation queries in
[`sql/validation_checks.sql`](sql/validation_checks.sql) are executed against
the public synthetic fixture generated by `create_synthetic_db.py`.

The synthetic fixture intentionally contains both valid control data and known
validation failures.

---

## Result Conventions

| Result type            | Meaning                                                                                   |
| ---------------------- | ----------------------------------------------------------------------------------------- |
| **VALIDATION FAILURE** | The query identifies a data-quality or consistency condition that should be investigated. |
| **INFORMATIONAL**      | The query provides diagnostic context and does not constitute a validation failure.       |
| `NULL`                 | The value is missing or unavailable. It is not treated as zero.                           |

The validation queries deliberately separate **missing values** from
**inconsistent values**.

## NULL Handling

The validation layer intentionally distinguishes between:

* **missing data** (`NULL`)
* **explicit zero**
* **explicit invalid values**
* **inconsistent values**

For example, `R_NULLS` has a missing `reported_num_trades`.

It is therefore detected by the dedicated missing-value check:

**Query 17 — Missing reported trade count**

It is **not** treated as a trade-count mismatch by Query 7.

The same principle applies to the other required fields:

| Field                 | Missing-value check |
| --------------------- | ------------------: |
| `initial_cash`        |            Query 15 |
| `metric_initial_cash` |            Query 16 |
| `reported_num_trades` |            Query 17 |
| `total_fees`          |            Query 18 |
| `final_equity`        |            Query 19 |
| `timeframe`           |            Query 20 |
| `num_bars_processed`  |            Query 21 |
| `total_return_pct`    |            Query 22 |

This prevents the validation layer from interpreting **missing data as zero**.

## Clean Control: `R_VALID`

`R_VALID` is the primary valid control case in the synthetic fixture.

It should **not** appear in the failure results for:

* trade-count validation
* total-fee validation
* initial-cash consistency
* total-return calculation
* date-range validation
* fee-rate validation
* quantity validation
* fill-price validation
* crypto annualization validation

### Control Values

| Field                   |      Value |
| ----------------------- | ---------: |
| `reported_num_trades`   |        `2` |
| Actual trade rows       |        `2` |
| `total_fees`            |     `2.00` |
| Actual fees             |     `2.00` |
| `initial_cash`          | `10000.50` |
| `metric_initial_cash`   | `10000.50` |
| `final_equity`          | `11000.55` |
| `total_return_pct`      |    `10.0%` |
| `timeframe`             |       `1d` |
| `num_bars_processed`    |      `365` |
| `annualized_return_pct` |    `10.0%` |

### Total Return

The expected total return is:

$$
\text{Total Return \%}
=
\frac{\text{final\_equity} - \text{metric\_initial\_cash}}
{\text{metric\_initial\_cash}}
\times 100
$$

For `R_VALID`:

```text
(11000.55 - 10000.50) / 10000.50 × 100 ≈ 10.0%
```

Therefore the reported `10.0%` passes the validation.

## Annualization Validation

The fixture contains both a crypto control using `binance` and a non-crypto control using `baostock`.

### Crypto Annualization

`R_VALID` uses the project crypto venue `binance`:

| Field                |     Value |
| -------------------- | --------: |
| Venue                | `binance` |
| Timeframe            |      `1d` |
| Bars processed       |     `365` |
| Total return         |   `10.0%` |
| Annualized return    |   `10.0%` |
| Annualization factor |     `365` |

The validation convention is **linear annualization**, not CAGR:

$$
\text{Annualized Return \%}
=
\frac{\text{Total Return \%} \times \text{Annualization Factor}}
{\text{Number of Bars Processed}}
$$

Therefore:

```text
10.0 × 365 / 365 = 10.0%
```

`R_VALID` therefore passes the crypto annualization check.

### Non-Crypto Annualization

`R_NONCRYPTO_CONTROL` uses the non-crypto venue `baostock`:

| Field             |      Value |
| ----------------- | ---------: |
| Venue             | `baostock` |
| Timeframe         |       `1d` |
| Bars processed    |      `252` |
| Total return      |    `10.0%` |
| Annualized return |    `10.0%` |

The validation logic **does not apply the crypto `365` factor** to this run.

Instead, it reports:

> **INFORMATIONAL:** non-crypto annualization uncheckable without exchange-calendar factor

A supplied exchange-calendar factor would be required to independently validate
the annualized return for a non-crypto market.

## Intentionally Broken Controls

The synthetic fixture contains specific rows designed to exercise individual
validation conditions.

| Synthetic Row         | Purpose                                                                |
| --------------------- | ---------------------------------------------------------------------- |
| `C_DUP`               | Duplicate candidate key                                                |
| `R_DUP_RUN`           | Duplicate run key and inconsistent reported trade count / fees         |

| `R_ANN_ERR`           | Incorrect crypto annualized return using the `binance` 24/7 convention |
| `R_NONCRYPTO_CONTROL` | Non-crypto annualization control case                                  |
| `C_BAD_FIT`           | Negative fitness                                                       |

## Query-by-Query Details

### Relationship and Key Validation

The first six checks validate the relationships between candidates, backtest
runs, and trades.

The expected results are:

* duplicate candidate: `C_DUP`
* duplicate run: `R_DUP_RUN`
* duplicate trade key: `R_DUP_TRADE`
* candidate without run: `C_DUP`, `C_ORPHAN`, `C_BAD_FIT` — informational
* run without candidate: `R_ORPHAN`
* trade without run: `R_MISSING_RUN`

These checks establish basic referential and uniqueness integrity before
performing metric-level validation.

### Reported vs. Derived Metrics

Queries 7–10 compare reported run-level metrics against values derived from the
underlying trade data or related run fields.

Expected failures include:

* `R_DUP_RUN` — reported trade count does not match actual fills
* `R_DUP_RUN` — reported fees do not match actual fees
* `R_BAD_MATH` — reported trade count does not match actual fills
* `R_BAD_MATH` — reported fees do not match actual fees
* `R_BAD_MATH` — `initial_cash` differs from `metric_initial_cash`
* `R_BAD_MATH` — reported total return differs from the calculated value

Missing values are handled separately by the required-field checks.

### Required Fields

`R_NULLS` intentionally contains missing values for required run-level fields.

The expected result is one failure from each applicable missing-field query:

* `initial_cash`
* `metric_initial_cash`
* `reported_num_trades`
* `total_fees`
* `final_equity`
* `timeframe`
* `num_bars_processed`
* `total_return_pct`

This produces **8 missing-field validation results**.

### Zero-Fill Runs

Runs with no associated trade rows are reported as **informational** rather than
automatically classified as failures.

Expected rows:

* `R_ZERO_FILL`
* `R_NULLS`

A zero-fill run may be legitimate depending on the strategy and test period,
so the validation layer surfaces it for review rather than declaring it invalid.

## Reproduction

Generate the synthetic database:

```bash
python3 create_synthetic_db.py
```

Then execute the queries in:

```text
sql/validation_checks.sql
```

using a SQLite-compatible client.

The synthetic database and CSV fixtures are generated locally and are intended
only for reproducible public validation.

## Scope

These expected results apply **only to the public synthetic fixture**.

They demonstrate that the validation logic can detect:

1. broken candidate/run/trade relationships;
2. duplicate keys;
3. mismatches between reported and derived trade metrics;
4. inconsistent cash denominators;
5. incorrect total-return calculations;
6. invalid numeric values;
7. invalid date ranges;
8. missing required values;
9. unsupported timeframes;
10. zero-fill runs;
11. incorrect crypto annualization;
12. the distinction between crypto and non-crypto annualization rules.

They are **not** intended to represent production trading performance,
profitability, or live-market behavior.
